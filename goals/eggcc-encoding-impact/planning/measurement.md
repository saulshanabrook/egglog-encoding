## Reuse the compiler collector; add native execution only for a promising lead

The existing collector and its usage doc already provide the useful compiler protocol:

- Externally supplied fixed manifest, explicit optimizer args, binary/cwd/engine/configuration labels and case origins; hashes of binary, input, listed artifacts and full CLI receipts. No builds, silent cache reuse or existing-result replacement.
- Separate untimed `--interp` runs requiring non-null equal `original_interpreted` and `result_interpreted`; the CLI itself does not compare these fields. Only after all correctness checks do warmups and measured optimizer invocations run without interpretation or diagnostic flags.
- Default one warmup and ten observations per arm, rotating starting arm each repetition. Exact scheduled order and complete nonempty measured rows are verified. Failing exits, signals, timeouts and interruptions remain explicit and halt the collection.
- Early successful/nonzero selected-test receipt checks; changed source/input/binary/receipt rejection. Tests cover these failures, timing/correctness separation, invocation from another cwd and figures derived from raw observations.
- Per-case SVG/PDF, raw `figure-data.json` and table, showing every observation, median, range and sample SD. No overall aggregate; displayed range is not a confidence interval.

Keep that compiler path small. It intentionally accepts only `--run-mode optimize`; it cannot already measure native program execution or backend preparation. The old process runner predates the primary checkout's memory guard. Select and record the intended current runner in the new worktree; do not overwrite the current guard with the old copy. Its normalized `wait4` child `ru_maxrss` remains **not simultaneous process-group peak**, combined host+Tiger live memory, encoding storage bytes or native runtime memory. New measurements must keep the same explicit scope.

Narrow extensions justified by the new cases are per-row UTC/monotonic start/end stamps, balanced block/order metadata, and an explicit separate native preparation/execution record if a native mechanism survives screening. Retain existing failure/provenance invariants. Native preparation records optimized Bril, lowering argv, compiler/Tiger/runtime/backend/tool hashes and executable hash; native execution records an argv array, actual runtime input tokens, exit/signal/timeout, stdout/stderr receipts, whole-process elapsed time and optionally a correctly labeled counter value. A small `scripts/eggcc_native_runtime.py` with focused tests is a proposed new file, not an existing CLI. Avoid a general benchmark framework or shell command-string executor.

The shared `run_command` owns reliable `wait4`, timeout and process-group cleanup but currently discards successful stdout/stderr. A native adapter needing exact output/counter receipts should add a narrowly reviewed optional retained-output sink to this helper, with existing guard behavior preserved; do not put a Python wrapper inside the timed child just to emit JSON, or duplicate wait/timeout machinery. Parse/check captured output after the timed interval. If only compiler impact is promising, do not add this native path.

## Execution and backend boundaries

`src/main.rs` reads `TestProgram::read_program()` and ignores parsed trailing `bril_args`; interpreter inputs come from retained `# ARGS:` headers. Optimizer flags and runtime input provenance are separate. Native executable args must be explicitly derived from the same fixture tokens and checked against the emitted `<executable>-args` sidecar. Use subprocess argv arrays, not the nightly runner's shell concatenation.

`src/util.rs:1096–1258` lowers through Brillvm with `runtime/rt.bc`, SROA, LLVM optimization, then native linking. LLVM enum spellings are `O0_O0`, `O1_O0`, `O2_O0`, `O3_O0`, `O3_O3`; nightly source confirms CLI forms `--run-mode llvm --optimize-egglog false --optimize-bril-llvm O3_O0`. Explicit unique `-o` paths per case/arm are required: default temp executable names do not identify the new feature mode. `--llvm-output-dir` names one output IR file despite its name.

The internal `llvm_compile_time` spans only the optimizing Clang invocation. It excludes EggCC, Brillvm lowering, SROA and final native compilation/link. `eggcc_compile_time` in the main CLI spans `Run::run()` and can include interpretation if enabled; do not use it as optimizer-only time in correctness runs. Collector external wall includes process launch, optimization/reconstruction and receipt writing. A timed analysis-only region requires an explicit instrumentation boundary and untimed validation that it encloses the same work for all arms; serialized node counts cannot stand in for time or peak memory.

**Backend gate before runtime sampling:** an EggCC/Bril load removal can be independently achieved by LLVM. Compile both emitted Bril arms with identical backend/runtime/options and inspect optimized IR plus final machine code for the affected loop. Use `O3_O0` for transparent saved-IR comparison and a predeclared `O3_O3` primary optimized-backend comparison; an `O0_O0` result is only a backend sensitivity control. For `O3_O3`, final compilation consumes the earlier SROA output with `-O3`, not the saved `optimized.ll`, so the saved file alone does not establish final code. Preserve exact executable/disassembly hashes; ignore address/debug-only differences when assessing the mechanism. If the intended difference disappears from final code, reject the native-speedup hypothesis for that input/backend before collecting a cohort. Compiler/analysis impact can still qualify separately.

Built-in `--add-timing` is useful only after checking the actual emitted program and generated instrumentation. Cached Brillvm `llvm.rs:1613–1705` inserts start at `_main` entry, after wrapper argument parsing, and stop before a main-level Print. Each such Print must be last or immediately followed by Return; it asserts if no timing was added. The interval includes in-main allocation, initialization, called functions, frees/checksums before the final print; prints in called helpers can be inside it. It excludes spawn, loader, wrapper argument parsing and final main print, not all setup. At `runtime/src/main.rs:21–31`, arm64 reads `cntvct_el0`: label **elapsed counter ticks**, not CPU cycles or seconds without a frequency receipt. x86 uses the runtime's RDTSC sequence; retain that counter definition and platform. Do not mix architectures/units.

Uninstrumented native wall includes spawn/loader/argument parsing/setup/output/teardown. Prepare and validate executables outside sampling; never include compiler builds or LLVM lowering in native runtime rows. A short process or setup-dominated workload may not resolve a kernel change. Prefer an existing sufficiently long workload; any batching, kernel-only harness or scaling is a separately justified derived case. Instrumented and uninstrumented binaries get separate hashes and same-kind comparisons.

`src/lib.rs:119–142` explicitly checks exit status in the counter executable branch but the uninstrumented executable interpreter branch reads stdout without checking status. A new native validator must require exit status 0, no signal and no timeout as well as exact expected stdout; equal stdout alone is insufficient. This is an infrastructure limitation found by source inspection, not a claimed baseline miscompilation. An ordinary `--interp` LLVM run also deletes its uninstrumented executable afterward (`util.rs:1003+`); compile retained native artifacts without `--interp`, then validate them explicitly.

The existing `infra/profile.py` offers a useful two-stage emit-Bril/lower/run pattern and raw counter arrays, but should not be the small study runner: `run_profile` builds automatically, clears a temp directory and can compile in parallel; backend compilation and native samples currently have no timeout; its shell-string sampling lacks the new exact provenance protocol. Its normal 2/100 and paper 10/200 warmup/sample counts are conventions, not demonstrated precision for this case. `tests/files.rs` runs source/output checks and snapshots for small tests and a separate `TestBenchmark` pipeline for slow/corpus cases; production CLI uses `non_weakly_linear=true`, whereas existing broad harness configs explicitly set false. Require actual production CLI receipts in addition to those tests.

## Controls, sampling and first measurement slice

Keep engine upgrade/adaptation separate from feature impact. The primary feature contrast should use the same engine, toolchain, compiler/Tiger/runtime/backend, input, contexts, schedule/pass count, extraction and thread configuration, changing only the documented feature/control settings. Use off, shared-analysis-without-consumer, query consumer and equivalent manual consumer when supported. The old off→keys contrast included extra memory/type closure and audits; query/manual shared that closure and query-based auditing. Do not call those contrasts pure encoding overhead or pretend the manual arm is query-free. Revalidate equivalence/domain/closure for the new candidate. Separate a compiler consumer contribution from a generic Const-guard optimization or an unrelated backend change.

Prior data cautions against accepting a single small median difference. Frozen feature-control fresh-allocations medians were .1429s off and .1488/.1490/.1493s keys/query/manual, n=10 each. A separate fresh reproduction had .1726/.1570/.1738/.1831s, with SD .03506/.03917/.04626/.05904s and observed maximum .3184s. Those distinct cohorts remain separate, with no causal explanation for noise inferred here. Source tables are `.../feature-control/figures/table.md` SHA256 `ef210d46ed5f1c9b4c3858b2daeb967fdd2af7ba7cdf1a1ffff4fb86cc640952` and `.../reproduction/figures/table.md` `ad9e6231fb58f01583bfed222041b1c5803e139b0f1700292db43d922356c6af` under the old raw root.

Proposed sequence after goal approval:

1. Freeze one candidate's law, consumer domain, feature/manual arms and expected positive/negative behavior. Run small semantic canaries and bounded untimed actual-CLI diagnostics, then screen existing `mat-mul`/`csrmv` only for eligible and applied consumer hits. Interpreter checks may use explicitly labeled small header variants first; performance inputs retain original headers. Do not assume the original large interpreter check is cheap. Record timeouts/unsupported cases, not fabricated evidence.
2. Select the first real hit-bearing workload plus an alias/unsupported negative control. Keep diagnostic egraph dumps, row counts and transformation receipts untimed. Verify all pass/config/output receipts. If aiming at native runtime, finish the same-backend final-code gate first. A removed Bril operation alone does not advance the impact objective.
3. A compiler pilot can use the existing one warmup/ten measured observations per arm and a 300s explicit timeout, chosen before launches. Including correctness, this is 12 invocations per case/arm, or 48 per case with four arms; the pilot is mechanism/noise screening, not the final speed claim. Native pilot count/timeout/metric are separately declared; no native collection until preparation/output checks pass.
4. If promising, freeze inputs/configuration and a new independent confirmation cohort before observing it. Use one measurement owner and no simultaneous builds, tests or other collectors. Balance complete arm orders within blocks; four-arm rotations over a multiple of four rounds avoid the old ten-round imbalance. Retain round/order/time stamps, host architecture/OS/backend, power/thermal observations if available and all raw samples. Fixed single-thread settings must match both arms. No post hoc outlier deletion, pooling of distinct cohorts or selective best-backend reporting.
5. Predeclare confirmation sample budget/precision target from pilot variability and an independent reproduction block; compare paired within-round effects per workload, with uncertainty computed over complete balanced rounds (e.g. a seeded bootstrap of log runtime ratios). Report raw values, absolute times, median/range/SD and the stated interval method, not a guessed interval derived from min/max. If uncertainty includes no benefit, report unresolved/neutral/regression and change the hypothesis or workload on evidence; do not chase significance by repeatedly extending the same cohort. Native startup dominance or erased code rejects that native claim without rejecting a separately supported compiler speedup.

For a genuine-bug lead, timing is optional: minimize the valid source, bind a sound violated invariant, reproduce baseline failure and candidate correction with negative controls and retained actual executable exits/outputs. A source comment, seeded graph conflict, invalid annotation, timeout of unknown cause or harness weakness alone is not a genuine baseline compiler bug.
