## Verified constraints that bound the search

**Engine mechanism, as implemented in the frozen worktree.** The `:injective` flag generates one union rule for equal-output applications and one panic rule per primitive field, run only when the `injectivity` ruleset is scheduled (`/Users/saul/p/wt/egglog-encoding/eggcc-encoding-payoff/egglog-experimental/src/injectivity.rs:209-292`). The read predicate `known-disequal?` searches stored assertions, forward steps through marked constructors, and reverse congruence through any constructor when every other sibling is already equal; it is sound, incomplete, creates nothing, and needs `:naive` in rule bodies (`disequality.rs:264-411`). `disequal` is an action usable in rule heads. Under NEE, a self-pair after a merge only populates a nullary relation that nothing reads unless `check-contradiction` is scheduled, and a stored self-pair still answers true to the query (`disequality.rs:21-27, 108`). Under EE, a self-pair collapses `T = F` globally. So NEE is the only safe representation for branch-scoped facts, and `check-contradiction` must never be scheduled in the compiler.

**EggCC's consumers of disequality and known-false, enumerated.** In the default schedule the only semantic disequality consumer is `NoAlias`, used by exactly one rule, write-then-load commute (`/Users/saul/p/wt/eggcc/encoding-payoff/dag_in_context/src/optimizations/mem_simple.egg:71-81`), which then enables store-forward and duplicate-load. The only known-false consumers are the Bool-bound rules that fold an expression to a false constant and eliminate an `If` (`interval_analysis.egg:108-114, 285-291`). Every other `!=` in the rule base is a raw-ID or primitive guard. The `Eq` branch rules transfer bounds only in the true branch (`interval_analysis.egg:409-432`); there is no false-branch flow and no equality union in the true branch either. `NoAlias` is pushed into `If` regions but not into loops (`mem_simple.egg:11-18`).

**Where sound cancellation can exist.** Walking every constructor in `schema.egg`: `Single` cancellation already follows from the `Get` rule (`util.egg:59`); `Bop`, `If`, `DoWhile`, `Function`, `Concat`, `Alloc`, `Call`, `Get` are each refuted by an existing rule that unions applications with different children, for example commutativity, `swap-if`, `loop-unroll`, `rec-to-loop`, and Concat associativity. The one remaining sound target is fixed-split `Concat`, and the projection closure in `util.egg:58-105` plus `SubTuple` reconstruction in `canonicalize.egg:93-107` already derives every component equality for any tuple that has a `Get`. Type structure was done in the combined study.

**Production configuration facts that change the demand picture.** The CLI forces `non_weakly_linear: true` (`/Users/saul/p/wt/eggcc/encoding-payoff/src/main.rs:173`), so the once-run pass makes every load state-transparent (`non_weakly_linear.egg:20-23`). Intervening loads therefore never block forwarding; only an intervening store to a possibly-aliasing address does. The optional points-to `memory` ruleset is unscheduled (`schedule.rs:101, 120`). Inlining runs two iterations. The lowering contains no `noalias` annotations anywhere in the tree, so backend alias knowledge comes from LLVM's own malloc semantics, which is a hypothesis to screen rather than a fact.

**Suite shapes.** No benchmark uses `band`, `shl`, `shr`, `smin`, or `smax`. The only index-equality guard around memory in the mem suite is quickselect's `ipos == kpos`, whose branches return immediately. Partition loops guard on loaded values, not indices, and polybench kernels are loop-carried store/load chains with no same-region store-then-reload. This matches the earlier C2 zero-demand finding and extends it: the demand is absent for any same-base symbolic-index disequality, not only for bounds-based pairs.

**Hazard for any `LessThan` producer.** Canonicalization unions `x >= y` with `y < x+1` and `y-1 < x` unconditionally (`canonicalize.egg:14-38`), the known signed-endpoint unsoundness. A predicate e-class can therefore contain a `LessThan` node whose true branch does not imply the disequality at the wrap endpoint. Producers must match `Eq` and `Not Eq` only until that canonicalization is guarded.

## The four known leads, challenged, plus the new families

**F1. Guard-derived index disequality, shifted, into same-base `NoAlias`.** This is the refined form of both the scoped fixed-shift lead and the Bitand lead.

- Law. In the region under `InIf false (Eq (Get inputs i) (Get inputs j)) inputs`, the universal pointwise fact `(Get ctx i) ≠ (Get ctx j)` holds for every feasible region input. Also `(Not (Eq ..))` true branches, since `swap-if` and `And`-splitting produce both forms. Forward through a unary `Succ`/`Pred` wrapper is sound because plus or minus one is a bijection modulo 2^64; forward through `Mul` by an even constant is not, and must be a negative control.
- Equality-sort intermediate. `Succ (Get ctx i) ≠ Succ (Get ctx j)` over Expr children, derived by the generic forward step from the stored index fact, then consumed as `NoAlias (PtrAdd a (Succ i)) (PtrAdd a (Succ j))` by a one-line bridge that requires the same base e-class. Same-base is a manual premise because `PtrAdd` is not jointly injective; the peephole `ptradd(ptradd(p,x),y)` would otherwise force a panic.
- Producer and consumer. Producer is new, four short rules mirroring the existing `Eq` true-branch rules, plus push-into-If and loop-passthrough transfer mirroring `interval_analysis.egg:435-459`. Consumer is the existing commute, then duplicate-load or store-forward.
- Source shape. A hot loop containing `if (i != j) { x = load a+(i+1); store a+(j+1), f(x); y = load a+(i+1); use y }`. With loads transparent, the second load sits on the store's state; `NoAlias` commutes it, duplicate-load merges it with the first. One load per iteration disappears. This is source-derived, not in the suite; label it so.
- Why a one-constructor primitive rule cannot reproduce it. There is no primitive anywhere in the chain; both the stored fact and the derived fact are over Expr e-classes, and the consumer is an existing optimization rule rather than a panic.
- Controls. Knockout: remove `:injective` from `Succ`, keep everything else; the query returns unknown and the load stays. Mediation-rescue: with the knockout in place, seed `(disequal (Succ i') (Succ j'))` directly; the load disappears again. Downstream-consumer: keep facts, disable the bridge; load stays. Manual comparator: a hand-written `IndexNE` relation with explicit `Succ`, `Pred`, and push rules deriving the same `NoAlias`; expect equal results and compare rule counts, not detection power. Negatives: `i == j` feasible path, a dead outer branch with `i == i`, mismatched shifts, `2*i` versus `2*j`, a `LessThan` guard at the signed endpoint, and a different base pointer.
- Earliest cheap falsifier. Before any build, inspect the baseline's optimized Bril and the LLVM output for the kernel with the second load manually deleted. If the baseline already prints the same native code, the backend erases the gain and the family is dead for runtime payoff. LLVM's BasicAA has a two-variable-index path that can call `isKnownNonEqual`; whether LLVM 18 feeds a dominating `i != j` into it is unverified.
- Likely outcome. Speedup, not bug. Runtime speedup on a source-derived kernel is plausible if the backend check passes; a suite-wide speedup is not, because the suite has no demand.
- Scope. Small, .egg only, no IR change. Roughly thirty lines plus tests. Risk is in the producer's exact matching of region inputs after context propagation, which the interval `Eq` rules already demonstrate.

**F2. Guard-derived disequality into redundant inner-`Eq` elimination.** This is the C5 lead with the pointwise model made explicit.

- Law and intermediate. Same stored facts as F1. The consumer bridge is `(rule ((= e (Bop (Eq) a b)) (known-disequal? a b)) ((set (hi-bound e) (BoolB false))) :naive)`, after which existing rules fold and eliminate the inner `If`. The pointwise reading is what makes it sound: the fact is "unequal at every feasible input of this region", which is exactly what folding needs, and the context partition of the e-graph keeps it scoped because every leaf carries its assumption and the single-context invariant is already error-checked (`context_of.egg:15-21`).
- Nontriviality. In the natural shape the inner predicate's operands are the same `Get ctx` nodes, so the query is a lookup and requirement 1 fails. It passes only when the inner check is over shifted operands, or when reverse congruence through a shared operand is needed, for example `(Eq (Add i c) (Add j c))`. Those are rare in real code.
- Source shape. Redundant guard after inlining: a callee guarding `if (i == j)` invoked under a caller's `i != j`. The suite's recursive quickselect does not produce it because the recursive call changes the indices.
- Controls. As F1, with If elimination as the observable. Negative: inner check with one operand replaced by a loop-carried value, which must stay unknown.
- Falsifier and outcome. LLVM's correlated value propagation folds this trivially, so the native speedup is near zero; compile-time payoff is negligible. Treat F2 as a mechanism exercise that rides on F1's producer, not as a standalone endpoint.
- Aside worth a separate ticket. The true `Eq` branch never unions `(Get ctx i)` with `(Get ctx j)`; adding that one manual union is a plain baseline optimization and a stronger comparator for anything in this family.

**F3. Fixed-split Concat cancellation beyond projection closure.** Law: equal concatenations with equal left lengths have equal lefts and rights, sound only for pure finite tuples with matching contexts. Intermediate fact is an Expr equality of tuple components. Consumer would be `passthrough` and loop rules. Why the primitive rule cannot do it: the children are Expr. Controls are the standard knockout and comparator. The earliest falsifier is a read-only diagnostic over exported pass graphs: count e-classes holding two `Concat` nodes with equal-length lefts in different e-classes after helpers saturate. I predict zero, because `Add-Gets` runs from every `Get` and leading-region rules create a `Get` for every region tuple; `swap-if` output tuples, the one case I could construct, are covered by `Add-Gets`. Outcome: compile-time only, and no work is avoided since the projections are created regardless. Scope: trivial. Verdict: run the diagnostic once and close.

**F4. Genuinely fresh live-region `NoAlias` with a blocked hot consumer.** Challenge: the hard part is not liveness. For a valid program, two pointers derived from distinct `Alloc` e-classes in one region never alias at any access where both are valid, since the interpreter never reuses addresses and native reuse requires a prior free that would make the access invalid. The LocalCell prototype's liveness tracking is a conservative over-approximation, and I state that as a hypothesis for the semantics reviewer. The real problems are elsewhere: the intermediate fact is node identity of allocation events, not a semantic Expr disequality, so the generic mechanism contributes nothing nontrivial, and asserting `disequal` on `Alloc` nodes is hazardous because store-forwarding legitimately merges states, after which a stored self-pair still answers true to the query. The blocked hot consumer also does not exist in `mem-simple`: the payoff shape is hoisting a loop-invariant load across a loop whose stores hit other arrays, as in gramschmidt's `R[k][k]` reloads, and that is a new loop-memory consumer. LLVM already hoists such loads when it knows the mallocs are distinct, which it usually does after inlining. The fair comparator is simply scheduling the existing `memory` ruleset. Falsifier: enable `memory` on an unrolled kernel and compare native code; if LLVM output is unchanged, close. Verdict: fails requirement 1 and likely fails the backend; do not build keys.

**F5. Lowbit normalization at signed minimum.** A source-derived bug lead that pre-exists in the baseline rule base. The data rewrite unions the odd-part output with `n / (n & -n)` (`hackers_delight.egg:86-101`). At `n = MIN` the source loop ends with odd part `-1` and factor `MIN`; the rewrite yields `MIN / MIN = 1`, and unary `Neg` uses plain Rust negation (`interpreter.rs:340`), so a debug interpreter would panic where the source does not. The suite's fenwick loop only returns the factor, so the bug is latent there and needs a variant that uses the odd part. This is a plausible new baseline bug, but its natural detector is the disqualified primitive-observation audit, and I found no nontrivial mechanism that reaches it. Recommend filing it as a plain EggCC bug report after a cheap reproduction on untouched main, and not counting it toward the study.

**Closed or negative ideas, recorded so they are not re-derived.** Same-mask `Bitand` reverse disequality: the reverse step is generic and real, but no source producer exists in the suite and the only `Bitand` is compiler-generated; keep as an engine test only. Injective `Assumption`, `Function`, `Alloc`, or `Cons`: either never fire or are unsound. `Term` disequality: Terms are never unioned, so injectivity is vacuous. Tuple-shaped observation wrappers: structurally the disqualified pattern. Switch-predicate refinement in `InSwitch` branches: a real missed analysis, but bounds-based and not encoding-related. Compile-time wins from replacing materialized `NoAlias` pairs: the pair counts are tiny, so there is nothing to save.

## Ranking and a finite search strategy

| Rank | Family | Meets requirement 1 | Payoff type | Main risk | Scope |
|---|---|---|---|---|---|
| 1 | F1 shifted-index disequality into `NoAlias` | Yes, via `Succ` forward step over Expr | Runtime speedup on a source-derived kernel | No suite demand; backend may already do it | Small .egg change |
| 2 | F2 inner-`Eq` elimination | Only with shifted or shared-operand inner checks | Compile-time, negligible | LLVM folds it anyway | Rides on F1 |
| 3 | F3 fixed-split Concat | Yes | Compile-time | Predicted fully redundant | Diagnostic only |
| 4 | F5 lowbit at MIN | No | Baseline bug | Detector is disqualified | Bug report only |
| 5 | F4 fresh regions | No | Runtime | Backend erasure, existing `memory` ruleset is the comparator | Medium, new loop consumer |

**Procedure.** Run these in order, each with a hard stop and a written failure note.

1. **Backend screen for F1, no build.** Hand-edit the proposed kernel's Bril to remove the redundant load, lower both versions through the pinned baseline's LLVM path, and diff native code. Also run the F3 diagnostic over exported graphs of the full suite. If the F1 diff is empty, F1 and F2 are closed for runtime payoff and the study pivots to F5 as a non-qualifying bug report.
2. **Producer slice.** Implement the `Eq`-only producer with NEE, push-into-If, loop passthrough, the `Succ`/`Pred` wrappers, and the same-base `NoAlias` bridge, default-off. Register positive, feasible-equal, dead-branch, mismatched-shift, even-multiplier, and signed-endpoint tests before enabling. Confirm the four controls on the kernel.
3. **Measurement.** Only if step 2 removes the load and step 1 showed the backend does not: ten repeated native runs per arm on the same kernel with matched configuration, reporting compile time and generated-program time separately, baseline versus candidate versus manual comparator.
4. **Breadth pass.** After each family closes, spend one bounded session enumerating new producers of universal pointwise facts in the actual pass-2 inlined graphs, since inlining is where redundant guards and same-base accesses could appear that the source files hide. Stop when that enumeration adds no new consumer demand.

**Stop rules.** Stop when every family is closed by its falsifier, or when the only remaining option requires a new loop-memory consumer or a points-to redesign, which is the F4 boundary. A negative result is recorded as "no qualifying payoff found in this search space", with the F3 diagnostic counts, the F1 backend diff, and the F5 reproduction kept as evidence. It is not a success and must not be rounded up to one.

**My overall assessment.** The two requirements jointly are hard to meet in EggCC, for reasons now grounded in source rather than in prior study outcomes: the compiler has one semantic disequality consumer with no demand on its suite, one sound cancellation target that projection closure already covers, and a bug-detection story that naturally lands on primitive conflicts. F1 is the only family where the generic mechanism does real work and the payoff could survive the backend, and it needs a source-derived workload to show anything. I would run step 1 first because it is cheap and decisive, and I would expect to be writing a negative report with the lowbit bug filed separately.
