# Find a richer joint encoding case in EggCC

## Approach and success boundary

Start with a concrete existing consumer: EggCC's type-mismatch checks. Test whether injectivity of free type constructors plus structural disequality can implement the check over nested equality-sort data. Compare the original check, an equivalent manual structural analysis and the encoding-backed version. This is a proposed integration, not a finding established during setup.

A richer integration can satisfy the [accepted facts](facts.md) without a new bug or speedup, although those are preferred. The positive result must show both features contributing to the **same reached consumer**. An annotation beside an unused query, another unary Boolean payload panic, or an engine-only example does not suffice. Hand-codability is expected and is not a rejection criterion.

If this route fails or proves unhelpful, investigate the remaining source-backed candidates with explicit rejection gates. A reviewed negative for the investigated scope is an acceptable result. Preserve the existing Boolean-observer study as a small fallback, without counting it as this goal's richer result.

Setup performed read-only discovery and created this goal package. Implementation and experiments begin when this goal is launched. The detailed inputs are [consumer discovery](planning/consumers.md), [encoding contracts](planning/encoding.md) and [verification entrypoints](planning/verification.md).

## 2. First vertical slice: structural type mismatch

### Existing data and consumer

Use the current free metadata constructors `PointerT`, `Base`, `TupleT` and `TCons`. The actual producer/consumer edge is:

```text
Function's declared output → ExpectType(body, expected)
body's type analysis      → HasType(body, actual)
structural disequality(expected, actual) → the existing mismatch diagnostic
```

The relevant implementation surfaces are `dag_in_context/src/schema.egg`, `schema.rs`, `type_analysis.egg`, schema/prologue assembly in `lib.rs`, and `schedule.rs`. A second endpoint is the existing loop input/output TypeList check. Exact source lines are in [consumer discovery](planning/consumers.md#1-c6-structural-type-disequality-in-the-existing-mismatch-check).

First choose a mismatch in a non-head tuple slot, for example `PointerT(IntT)` versus `PointerT(BoolT)` with otherwise identical tuple structure. The desired inference is:

```text
IntT ≠ BoolT                         [justified explicit type-tag law]
⇒ PointerT(IntT) ≠ PointerT(BoolT)    [marked structural constructor]
⇒ nested TCons values differ        [multiple equality-sort fields]
⇒ TupleT values differ              [marked structural constructor]
⇒ actual ExpectType consumer reports the mismatch
```

Do not assert the final parent mismatch as a premise. The inference must cross existing composite type values and reach the actual check.

This route uses injectivity-backed **forward structural disequality**. It need not run equality-sort cancellation or remaining-child reverse inference; report that distinction. Do not force an additional cancellation example merely to claim more features.

### Semantic and domain gate

Before implementation, write and review the exact finite free-type contract. Constructor-name disjointness is an additional law, not an effect of `:injective`. Explicitly justify the required base-leaf, leaf/pointer, Base/TupleT and TNil/TCons distinctions over present supported values; never seed them from raw ID `!=`. Compare a manual structural checker using the same laws.

Keep `TLConcat`, `TypeList-ith` and `TypeListRemoveAt` unmarked: their ordinary normalization is not injective. Preserve the helper schedule. Initially cover normalized, fully known finite types. `TmpType`, Unknown and symbolic forms remain outside that supported replacement, with an explicit existing-check/unsupported path. Query unknown is not a passed type check. Test that legitimate normalization never contradicts a seeded distinction.

The front end already rejects ill-typed source. Therefore the first failing fixture may be an **internal EggCC type-analysis input**, explicitly labeled as such. It must exercise the real Function→ExpectType and type-producer rules, not just call `known-disequal?` on a detached graph. It is not a newly discovered valid-source compiler bug. Valid typed source controls must also traverse the actual native pipeline.

Reject or narrow this slice if it requires a general type-unifier redesign, unsafe helper annotations, unsupported forms silently passing, or only a forced final disequality with no meaningful consumer.

## Risks and open questions

- Structural type checking may be a useful encoding integration while adding no capability beyond the current guard; report that tradeoff honestly.
- Explicit type-tag constraints need a sound supported-domain policy and may cost more rows/work than the raw check. Avoid derived-pair or performance claims without measurement.
- A first internal type-analysis failure does not imply a valid-source bug; meaningful normal-pipeline coverage must be demonstrated separately.
- Fixed-split tuple work may already be redundant. Scoped-value inference is limited by impossible-context isolation; pointer keys need a real live-provenance producer.
- Query consumers see committed tables, require appropriate scheduling and treat unknown as unknown. None of the proposed steps promises unrestricted closure or proof support.
